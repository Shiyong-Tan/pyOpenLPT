# Exact GPU-assisted image preprocessing

## Scope

GPU preprocessing is now attempted by default when CuPy can initialize a CUDA
device.  The GUI and CLI both retain a `CPU only (significantly slower)` option.
Missing CuPy, an unavailable device, or a CUDA failure automatically retries the
affected image through the authoritative CPU pipeline.

This change does not move the whole preprocessing workflow to the GPU.  It
keeps operations on the device only while that avoids unnecessary transfers and
can reproduce the existing output exactly.

## Operations performed on the GPU

One image upload covers these pointwise operations:

- optional float32 background subtraction and zero clipping;
- power-of-two bit-depth scaling;
- conversion and clipping to uint8;
- optional intensity inversion; and
- intensity-range adjustment through a 256-entry lookup table.

The final uint8 image is downloaded once.

The intensity lookup table is generated by the existing CPU
`imadjust_opencv()` implementation.  The GPU only performs integer table
indexing, preventing different CPU/GPU floating-point rounding from changing a
pixel.

## Operations intentionally kept on CPU

- TIFF/CINE decoding and TIFF writing;
- color-to-grayscale conversion through OpenCV;
- mean-background construction; and
- the existing OpenCV erode/blur/sharpen denoise sequence.

These stages either depend on host libraries or are kept on CPU to preserve the
exact existing byte output.  In particular, this design does not repeatedly
transfer an image for individual preprocessing controls.

## Batch behavior

Per-camera background arrays are uploaded once and reused.  GUI and
programmatic batch workers pass the selected mode through every frame.  A CUDA
exception causes that frame to be recomputed on CPU before it is written, so a
GPU failure cannot silently produce partial numerical output.

The CLI adds `--cpu-only`.  Omitting it enables GPU assistance with automatic
CPU fallback.

## Exactness verification

The branch passed 210 CPU/GPU comparisons with zero differing pixels.  The
cases cover:

- every uint8 input value under multiple integer and fractional intensity
  ranges, inversion modes, and bit shifts;
- randomized uint8/uint16 images with float32 backgrounds;
- optional OpenCV denoising; and
- 60 representative T3 camera/frame/setting combinations.

A representative CPU/GPU TIFF pair had identical SHA-256 hashes.  A separate
parallel six-image batch test also produced byte-identical TIFF files and image
lists in CPU-only and GPU-assisted modes.

Earlier 100-image T3 measurements of this implementation found approximately
4.77x compute-only speedup without denoising and 1.36x to 1.42x with denoising.
The lower denoise gain is expected because that exact OpenCV stage remains on
CPU.
